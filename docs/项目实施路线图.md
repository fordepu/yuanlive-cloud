# YuanLive 项目实施路线图

## 1. 文档目的

本文档基于当前代码库梳理已具备的能力、待补齐的业务闭环与后续实施顺序，用于指导开发排期和设计讨论。

当前项目已具备用户、权限、直播间、实时互动、视频、搜索、AI 对话、AI 推荐和直播内容风控等基础能力。后续工作不应平均铺开，而应优先完成能够形成用户价值和资金闭环的能力。

## 2. 当前基线

### 2.1 已具备能力

| 领域 | 已实现能力 |
| --- | --- |
| 基础架构 | Spring Cloud 微服务、Gateway、Nacos、Redis、RabbitMQ、MySQL、MongoDB、Elasticsearch、MinIO、SRS、Flink、XXL-JOB、Seata 等运行基础设施。 |
| 用户与权限 | 注册登录、验证码与找回密码、Token 刷新、二维码登录、用户搜索与推荐、关注关系、主播申请、RBAC、管理端用户/角色/菜单管理。 |
| 文件能力 | MinIO 普通上传、分片上传、断点检查和分片合并。 |
| 直播核心 | 创建/申请/开播/停播、房间列表与详情、SRS 回调、WebSocket 加入/离开、群聊、单聊、点赞、在线状态和房间热度。 |
| 内容与推荐 | 直播分类、视频资源、点赞/取消点赞、观看行为、热门搜索、ES 搜索、Flink CDC 同步、行为驱动的推荐基础。 |
| AI | 流式对话、会话与消息历史、会话置顶/删除、AI 推荐提问、MongoDB/Redis Checkpoint、联网检索与 MCP 配置。 |
| AI 风控 | 聊天消息收割、MQ 送审、风险工作流、风险决策节点。 |

### 2.2 已知缺口

1. 钱包服务、钱包实体与钱包客户端仅保留骨架，没有业务模型、接口、数据表和网关路由。
2. 礼物消息协议已存在，但没有扣费、收益、订单、幂等和结算逻辑。
3. AI 风控在进入人工审核节点时暂时自动放行，尚未形成后台审核闭环。
4. 直播消息内的 VIP 和等级字段固定为 `false`、`0`，会员和等级体系尚未落地。
5. 分类删除没有校验是否被直播间引用。
6. AI 多模态输入、工具结果回传、引用来源仍是待实现字段。
7. 自动化测试较少，尚未覆盖关键业务链路。

## 3. 实施原则

1. 先补业务闭环，再扩展功能面。钱包、礼物、收益和风控决定平台是否能安全运行。
2. 涉及资金、直播状态和风控状态的操作必须具备幂等、审计记录和可追踪性。
3. 跨服务业务以本地事务加可靠消息最终一致为默认方案；不以分布式事务替代业务幂等。
4. 对外接口先明确状态机、错误码和权限边界，再落表和编码。
5. 每个阶段结束均应有接口测试、关键服务测试和可演示的验收场景。

### 3.1 已确认的产品决策

| 决策项 | 结论 | 实施约束 |
| --- | --- | --- |
| 首期资产类型 | 采用平台虚拟货币（下文暂称“金币”） | 固定兑换率为 `1 元 = 10 金币`；金币与法币支付隔离；所有余额、价格、收益和流水以整数金币存储；首期不提供提现。 |
| 自动化集成测试 | 采用 Testcontainers | 测试按服务启动最小依赖集合，不依赖开发机已有中间件或整套 Docker Compose 环境。 |
| 分类删除规则 | 被直播间引用的分类严格禁止删除 | 返回可读的业务错误；不自动置空分类，也不自动迁移直播间。 |

首期的“充值”可以先实现为受控的模拟入账能力，保留支付订单和渠道适配接口，但不直接接入真实第三方支付。后续接入支付渠道时，只能通过已支付订单向钱包入账，不能由客户端直接修改余额。普通用户金币只能用于消费，不能兑换或提现；主播收益仅用于平台内统计和榜单，不提供法币结算或提现。

## 4. 分阶段计划

### 阶段 0：工程基线与风险收口

**目标：** 在新增核心业务前，建立可验证、可回滚的工程基础。

**当前进度：** 已完成分类引用删除保护、HTTP `traceId` 透传与回传、登录/开停播/WebSocket 群聊/AI 会话入口的基础测试，以及直播服务的 MySQL、Redis、RabbitMQ 和 AI 服务 MongoDB Testcontainers 底座。风控送审队列已具备有限重试和死信路由，命中人工审核节点后不再自动放行。钱包、礼物等资金事件的 Outbox 与消费幂等记录将在阶段 1 伴随具体订单模型落地；现有普通通知消息不进行无差别重构。

**工作项：**

- 为用户认证、直播开停播、WebSocket 消息、AI 流式对话建立基础测试。
- 建立基于 Testcontainers 的 Redis、RabbitMQ、MySQL、MongoDB 集成测试方案；各服务仅启动测试所需的最小依赖集合。
- 统一关键操作日志字段：`traceId`、`userId`、`roomId`、`orderNo`、`eventId`。
- 补齐分类删除前的直播间引用检查；只要分类仍被直播间引用，就严格拒绝删除，不做自动迁移或置空。
- 核对网关、各服务端口和 Nacos 配置，补充环境变量说明，避免将密码和第三方密钥写入仓库。
- 为消息消费增加失败重试、死信队列、告警和人工补偿入口。

**验收标准：**

- `mvn test` 可在独立可写 Maven 仓库中执行。
- 关键状态变更有结构化日志和可查询的错误原因。
- 分类不能在仍被直播间使用时删除。
- 至少覆盖登录、开播/停播、发送一条群聊、AI 会话创建四条主路径。
- 集成测试可在无本地 Redis、RabbitMQ、MySQL、MongoDB 环境的机器上独立执行。

**难点与设计要点：**

- 不要让测试依赖开发机已有的 Nacos、Redis 或数据残留；测试数据应可重复初始化和清理。
- 消息处理要采用“至少一次投递 + 消费端幂等”，不要依赖 MQ 恰好只投递一次。

### 阶段 1：钱包、礼物与收益闭环

**文档基线：** [PRD](./prd/2026-08-25-阶段1送礼资金闭环-prd.md)、[SPEC](./specs/2026-08-25-阶段1送礼资金闭环-spec.md)、[Plan](./plans/2026-08-25-阶段1送礼资金闭环-plan.md)。

**目标：** 让用户能安全送礼，主播能看到可核对的收益，平台能追踪每一笔资金变化。

**工作项：**

- 完成 `wallet-entity`：钱包账户、账户流水、充值订单、礼物订单和主播收益记录。
- 完成 `wallet-service`：余额查询、充值下单、支付回调、送礼扣费、退款/冲正、流水查询和收益统计。
- 完成 `yuanlive-wallet-client`：定义直播服务和用户服务所需的最小 Feign 契约。
- 在 Gateway 中增加 `/wallet/**` 路由，并在权限体系中增加钱包和财务权限点。
- 完成礼物目录、礼物价格、送礼接口和直播 WebSocket 广播。
- 以订单状态驱动扣款和广播：支付/扣款成功后才发布礼物事件，禁止客户端直接构造收益结果。
- 完成主播收益账户、平台抽成和收益统计；首期不实现提现、出金和法币结算。
- 对账与补偿：定时核对“订单、账户流水、礼物事件、主播收益”四类记录。

**已确认的金币模型：**

- 固定兑换率为 `1 元 = 10 金币`，礼物价格和余额均为整数金币。
- 用户充值获得消费金币；消费金币不可提现、不可转让，也不能由客户端直接修改。
- 用户送礼后，主播获得独立的收益金币；收益金币仅用于收益统计、榜单与后续结算准备，首期不支持兑换或提现。
- 礼物订单必须固化 `coinAmount`、`exchangeRate`、`platformRate`（万分比）和结算规则版本，禁止在查询历史订单时按当前配置重新计算。

**建议的核心状态机：**

```text
礼物订单：CREATED -> PAYING -> PAID -> DELIVERED
                      |         |        |
                      v         v        v
                   CLOSED    REFUNDING  REVERSED

账户流水：INIT -> APPLIED -> REVERSED
```

**验收标准：**

- 同一 `requestId` 重试送礼不会重复扣款、重复加收益或重复广播。
- 余额、账户流水、礼物订单和主播收益可以按订单号追溯。
- 余额不足、直播间已关闭、主播不可收款、重复请求、消息重复消费均有明确处理。
- 送礼成功后，观众和主播均能收到一次且仅一次可见礼物事件。

**难点与亮点：**

- **金额精度：** 金币使用 `long` 整数存储，禁止 `double`；首期固定 `1 元 = 10 金币`，兑换率和舍入规则作为订单快照保存。法币以“分”为最小单位的存储规则留待接入真实支付或结算时启用。
- **记账模型：** 推荐采用不可修改的流水账。余额是流水聚合后的业务快照，冲正以新增反向流水实现，不直接改历史流水。
- **一致性：** 扣款、主播收益和消息广播不能依赖一个远程大事务。推荐采用本地事务落订单与 outbox 事件，再由可靠消费者完成后续动作。
- **安全：** 支付回调必须验签、校验金额和商户订单，回调和内部送礼接口都必须幂等。

### 阶段 2：直播治理、会员与管理后台闭环

**目标：** 建立直播间的秩序、权益和运营管理能力。

**工作项：**

- 完成会员等级、经验值、勋章和用户直播间展示资料。
- 将 WebSocket 聊天和点赞中的 VIP/等级从固定值改为用户权益快照。
- 增加直播间禁言、踢出、黑名单、房管、敏感词、慢速模式和消息频控。
- 完成礼物与活动榜单：房间榜、主播榜、周榜、贡献榜。
- 完成主播申请审核、主播状态管理和开播权限校验。
- 为管理员补充风控审核列表、审核详情、通过/拦截/恢复直播等接口。
- 增加运营配置：礼物价格、抽成比例、会员权益、活动规则和风控阈值。

**验收标准：**

- 用户权益变更后，下一次进入房间及后续消息可展示正确等级/VIP 信息。
- 被禁言/拉黑用户无法继续发送消息或重连绕过限制。
- 风控命中后不会自动“批准”；管理员可以看到证据、做出决策并留下审计记录。
- 所有管理动作都具有操作者、原因、对象、时间和结果。

**难点与亮点：**

- **权益快照：** 直播消息应携带发送时的等级和 VIP 快照，避免历史消息随着用户升级而被错误改写。
- **实时权限：** 禁言和踢人状态放 Redis 并设置合理 TTL，同时以数据库记录保存长期规则；网关或 Netty 鉴权时读取缓存。
- **审核状态机：** 建议将风控状态设计为 `NORMAL`、`PENDING_REVIEW`、`RESTRICTED`、`SUSPENDED`、`RESTORED`，避免仅使用布尔值表达复杂业务状态。

### 阶段 3：AI 能力产品化

**目标：** 让 AI 从单一对话接口演进为可控、可解释、可运营的助手能力。

**工作项：**

- 完成多模态输入：文件先上传 MinIO，再将受控 URL 或解析结果传给模型。
- 完成 Tool Call 协议：工具定义、调用标识、执行结果回传、超时、失败和重试规范。
- 在响应中提供引用来源、检索片段和工具调用过程；前端可选择展示推理摘要，而非暴露完整内部推理。
- 为 Agent 设置建立白名单：模型、温度、最大 Token、联网开关、允许工具集。
- 增加 AI 使用配额、并发限制、内容安全检查和成本统计。
- 将直播 MCP 工具按只读和有副作用两类拆分；有副作用工具必须二次确认、鉴权和审计。
- 优化 AI 推荐任务：记录推荐版本、点击反馈和离线评估指标。

**验收标准：**

- 一次对话可安全处理文本和至少一种文件类型，文件访问不暴露永久公开链接。
- 工具调用可完整追溯 `conversationId`、`toolCallId`、入参摘要、结果、耗时和失败原因。
- 联网回答可返回可核验的来源信息。
- 用户无法通过 `agentSettings` 任意选择未授权模型、工具或突破配额。

**难点与亮点：**

- **工具调用闭环：** 将模型提出工具调用、服务执行、结果写回模型视为一个状态机，而不是一次 HTTP 转发。
- **安全边界：** 模型输出永远不可信。工具参数必须在服务端再次校验权限、数据范围、类型和危险操作确认。
- **成本治理：** 模型调用需要记录输入/输出 Token、模型版本、缓存命中和工具耗时，才能优化成本与体验。

### 阶段 4：可靠性、可观测性与运营规模化

**目标：** 让系统具备上线后的监控、排障、恢复和持续迭代能力。

**工作项：**

- 接入指标监控与告警：接口耗时、错误率、WebSocket 在线数、MQ 堆积、AI 耗时、支付失败率、直播开播成功率。
- 建立 OpenTelemetry 链路追踪，贯通 Gateway、Feign、RabbitMQ、AI 和数据库操作。
- 建立业务对账、补偿任务、死信重放和数据修复流程。
- 压测直播 WebSocket、热点直播间、搜索、礼物峰值和 AI 流式输出。
- 建立灰度发布、配置版本回滚、数据库迁移版本管理和故障演练。
- 为核心业务建立仪表盘：GMV、礼物转化、主播收益、留存、风控命中、AI 使用成本。

**验收标准：**

- 线上一次用户请求可通过 `traceId` 定位到跨服务调用和异步消息。
- 失败消息可安全重放且不会造成重复资金变动。
- 压测报告明确系统容量、瓶颈和扩容阈值。
- 核心告警有负责人、阈值和处置步骤。

## 5. 建议的交付顺序

```text
阶段 0：测试、日志、消息可靠性、分类约束
    -> 阶段 1：钱包账户 -> 礼物订单 -> 主播收益 -> 对账
    -> 阶段 2：人工风控 -> 房间治理 -> 会员与运营
    -> 阶段 3：AI 多模态 -> Tool Call -> 引用与配额
    -> 阶段 4：观测、压测、灰度、运营指标
```

阶段 1 可以在阶段 0 的基础测试完成后开始；阶段 2 的人工风控可与钱包开发并行讨论，但“自动批准审核”必须在正式环境启用前移除。

## 6. 需要确认的设计决策

以下事项会显著影响数据模型和接口，建议在开始阶段 1 前确认：

| 主题 | 需要确认的问题 | 建议默认方案 |
| --- | --- | --- |
| 资产类型 | 已确认采用何种资产模型？ | 已确认：首期采用虚拟金币，固定 `1 元 = 10 金币`；普通用户金币和主播收益金币均不可提现。 |
| 支付范围 | 首期是否接入真实第三方支付？ | 首期保留支付适配层和模拟支付，支付渠道实现可后续接入。 |
| 主播分成 | 抽成是统一比例还是按主播/公会/活动变化？ | 第一版采用平台默认比例，订单保存结算快照以支持后续差异化。 |
| 提现策略 | 是否首期开放提现？ | 已确认：首期不提供提现、出金或法币结算，仅保留收益统计数据。 |
| 风控处置 | 风控命中后是暂停发言、暂停直播，还是先转人工审核？ | 分级处置：低风险限流，中风险转人工，高风险自动停播并保留证据。 |
| 会员体系 | VIP 是付费订阅、等级成长，还是两者并存？ | 分离设计：VIP 表示付费权益，等级表示成长值。 |
| AI 联网 | 是否默认开启联网？来源是否展示给用户？ | 默认关闭，用户显式开启；联网回答返回可展示的来源引用。 |
| AI 工具 | AI 是否允许执行会改变业务状态的工具？ | 首期只开放只读工具；写操作必须用户确认、权限校验和审计。 |

## 7. 首个迭代建议

建议以“**送礼资金闭环 MVP**”作为首个正式迭代，范围控制如下：

1. 用户钱包开户、余额查询和虚拟金币充值模拟。
2. 固定礼物目录与价格。
3. 直播间送礼：校验房间状态、余额扣减、主播收益入账、实时广播。
4. 钱包流水、礼物订单和主播收益明细查询。
5. `requestId` 幂等、MQ 消费幂等、失败补偿任务和基础对账。
6. 管理员查看订单与人工处理异常订单。

该范围避免在第一轮同时引入真实支付、提现/出金、公会结算和复杂活动规则，但已经能够验证架构和最关键的资金安全约束。
