# 阶段 1 送礼资金闭环 SPEC

## 1. 架构与职责

`wallet-service` 是资金账务唯一所有者：钱包账户、充值订单、礼物订单、流水、主播收益和 Outbox 均在该服务的 `yuanlive_wallet` 数据库中。`live-service` 只负责房间预校验、可靠消费礼物事件和 WebSocket 展示，不能修改钱包余额、订单或收益。

```text
HTTP 送礼请求
  -> wallet-service：本地资金事务
  -> Outbox
  -> wallet.domain.exchange / gift.delivered
  -> live-service：Inbox 去重
  -> live.realtime.broadcast.exchange
  -> 各 live-service 实例本地 Netty 房间广播
```

资金数据使用 MySQL 本地事务强一致；展示、统计和通知采用可靠事件最终一致。阶段1不使用 Seata 替代订单状态机、唯一约束、Outbox、Inbox、对账和冲正。

## 2. 数据模型

### 2.1 主键与业务标识

阶段 1 的钱包核心表统一使用 CosId 雪花 `BIGINT` 作为 `id` 主键。应用侧生成主键，MySQL DDL 使用 `BIGINT NOT NULL PRIMARY KEY`，不得配置 `AUTO_INCREMENT`；实体主键使用 `@CosId` 和 `@TableId(type = IdType.INPUT)`，并引入 `cosid-mybatis` 插件，使 CosId 在 MyBatis 写入前赋值。

`IdType.ASSIGN_ID` 使用的是 MyBatis-Plus 自己的标识生成器，不等同于 CosId；钱包核心表不得使用该配置。

雪花 ID 的目标是全局唯一和按生成时间大致有序，不承诺数据库层面的严格连续递增。不要将它用于表达订单数量或业务顺序。

| 标识 | 生成方与格式 | 用途 |
| --- | --- | --- |
| `id` | CosId 雪花 `BIGINT` | 所有核心表的主键、内部关联和游标分页 |
| `order_no` | 服务端业务编号 | 用户展示、人工对账和跨表业务追溯 |
| `event_id` | 服务端全局事件标识；重试时保持不变 | Outbox/Inbox 消息幂等键 |
| `request_id` | 客户端为一次点击生成的 UUID | HTTP 请求幂等键，不替代数据库主键 |

订单列表使用 `id` 或 `created_at + id` 游标分页，不能依赖连续编号。业务唯一性仍通过订单号、`(sender_id, request_id)`、流水业务键与 `event_id` 唯一约束保证。

| 表 | 核心字段与约束 | 责任 |
| --- | --- | --- |
| `wallet_account` | `user_id UNIQUE`、`available_coin BIGINT`、`version` | 用户消费金币快照 |
| `wallet_ledger` | `ledger_no UNIQUE`、`business_type`、`business_no`、`direction`、`amount`、`balance_after`；`(business_type,business_no,direction) UNIQUE` | 不可修改资金流水 |
| `recharge_order` | `order_no UNIQUE`、用户、金币、状态、渠道交易号 | 充值状态与回调幂等 |
| `gift_catalog` | 礼物标识、名称、图标、单价、上架状态 | 服务端礼物数据源 |
| `gift_order` | `order_no UNIQUE`、`(sender_id,request_id) UNIQUE`、房间、主播、礼物、价格及结算快照、状态 | 送礼主单 |
| `anchor_income` | `gift_order_no UNIQUE`、主播、毛额、平台抽成、净收益 | 主播收益 |
| `outbox_event` | `event_id UNIQUE`、事件类型、业务单号、payload、状态、重试和租约字段 | 待发布领域事件 |
| `live_inbox_event` | `event_id UNIQUE`、状态、失败原因、处理时间 | 直播服务消费去重 |
| `event_replay_audit` | 原事件、操作者、原因、时间、结果 | 死信重放审计 |

金额、价格、收益与抽成结果均为整数金币。礼物订单必须固化 `coinAmount`、`exchangeRate`、`platformRate`（万分比）与 `settlementRuleVersion`。退款/冲正只新增反向流水，禁止更新历史流水。

## 3. 状态与幂等

```text
礼物订单：CREATED -> PAID -> DELIVERED
                    |        |
                    v        v
                 REFUNDING -> REVERSED

充值订单：PENDING_PAYMENT -> PAID
                    |
                    v
                 CLOSED

Outbox：NEW / PUBLISHING / RETRY_WAIT / PUBLISHED / DEAD
Inbox：PROCESSING / SUCCEEDED / FAILED
```

- HTTP 幂等键：`(senderId, requestId)`。已有成功订单返回原结果；处理中订单返回处理中；余额不足的同一请求可在充值后用原键重试。
- 账户并发控制：事务内按用户 `SELECT ... FOR UPDATE` 锁定账户，再检查并扣减余额；条件更新 `available_coin >= amount` 作为额外防线。
- 业务唯一键：流水、收益、Outbox 与 Inbox 都使用订单号或 `eventId` 的唯一约束防止代码或消息重试重复生效。
- 房间预校验不属于事务。扣款提交后房间关闭时，订单仍有效；不能因展示链路失败删除订单或直接修改历史流水。

## 4. 送礼与充值事务

### 4.1 送礼

1. 从 Token 获取送礼人，按 `requestId` 查询历史订单。
2. 查询上架礼物，调用 `live-service` 只读接口确认房间开播、主播可收礼。
3. 在一个 `@Transactional` 内锁定账户，检查余额，创建 `gift_order`，更新余额，写支出 `wallet_ledger`，写 `anchor_income`，写 `outbox_event(gift.delivered)`。
4. 提交事务后返回订单结果。任一数据库写入失败则全部回滚。

### 4.2 充值

创建订单只接收金币数量，服务端按固定汇率 `1 元 = 10 金币` 计算分币金额并初始化为 `PENDING_PAYMENT`。支付回调或模拟支付在事务内锁定 `recharge_order`。未支付订单更新为 `PAID`，增加余额、写入 `RECHARGE` 流水和 `wallet.recharged` Outbox；已支付订单校验订单归属后直接返回，不再次入账；`CLOSED` 等非法状态不得开户或入账。

模拟支付入口由 `wallet.recharge.simulation-enabled` 控制，默认值为 `false`，只允许开发或测试环境通过 `WALLET_RECHARGE_SIMULATION_ENABLED=true` 或对应 Nacos 配置显式开启。生产环境必须保持关闭，后续真实支付渠道只能调用同一受控支付服务，不得直接修改余额。

## 5. 接口契约

### 5.1 对外 HTTP

```text
GET  /wallet/accounts/me
POST /wallet/recharge-orders
POST /wallet/recharge-orders/{orderNo}/simulate-paid
POST /wallet/gift-orders
GET  /wallet/query/gift-orders/{orderNo}
GET  /wallet/query/ledgers?beforeId=<雪花ID>&limit=<limit>
GET  /wallet/query/incomes?beforeId=<雪花ID>&limit=<limit>
GET  /wallet/query/reconciliation/gift-orders/{orderNo}  （管理员只读）

网关的 `/wallet/**` 路由去掉第一段前缀后转发到 wallet-service；服务内部对应 `/accounts/**`、`/gift-orders/**`、`/recharge-orders/**` 和 `/query/**`。普通用户的订单查询按 Token 中的 `userId` 做归属校验，不能读取他人的订单；流水和收益只按当前用户/主播查询。游标使用 `id` 倒序查询，单页限制为 1 至 100，下一页使用返回的 `nextCursor`。
```

送礼请求只接受 `requestId`、`roomId`、`giftId` 和 `count`，其中 `count` 范围为 1 至 99。接口不得接受客户端传入的金额、主播、礼物图标、价格、抽成或收益。

### 5.2 Feign

`yuanlive-live-client` 新增：

```java
Result<GiftRoomValidationResult> validateGiftRoom(Long roomId);
```

结果包含 `roomId`、`anchorId`、`liveStatus`、`acceptingGifts` 和 `rejectionReason`。`yuanlive-wallet-client` 只公开跨服务必要的余额和订单查询，禁止提供直接改余额或创建流水的 Feign 接口。

钱包内部只读接口为 `GET /internal/wallet/accounts/{userId}` 和 `GET /internal/wallet/orders/{orderNo}`；直播内部只读接口 `GET /internal/live/inbox/{eventId}` 返回 `live_inbox_event` 的状态，供对账使用。对账以 `orderNo` 关联礼物订单、扣款流水、主播收益和 Outbox，再以 Outbox 的 `eventId` 查询直播 Inbox；缺失或非 `SUCCEEDED` 只进入异常列表，不自动补账、重发或修改历史流水。

### 5.3 Netty 与 WebSocket

Netty 仅显式处理 `PING`、`JOIN_ROOM`、`CHAT`、`LEAVE_ROOM`、`LIKE`。未知 `cmd` 返回错误；`CHAT(type=gift)` 返回“请使用送礼订单接口”，普通文本聊天保持不变。

`live-service` 生成的礼物展示消息必须携带 `eventId`、`orderNo`、房间、送礼人和礼物快照。客户端按 `eventId` 去重；该去重仅影响展示层。

## 6. 消息拓扑与策略

| Exchange | 类型 | 事件 | 策略 |
| --- | --- | --- | --- |
| `wallet.domain.exchange` | topic | `gift.delivered`、`wallet.recharged`、`gift.reversed` | 持久领域事实 |
| `wallet.domain.dlx` | topic | 资金事件死信 | 持久、人工重放 |
| `live.realtime.broadcast.exchange` | fanout | 聊天、入场、礼物展示、公告 | 跨实例 WebSocket 展示 |
| `live.stats.exchange` | topic | 点赞、热度、观看增量 | 可聚合统计 |

`live.gift.delivered.queue` 为 durable 队列，绑定 `wallet.domain.exchange/gift.delivered`，使用手动 ACK、1/2/4 秒有限重试和 Inbox。不可恢复负载显式 reject，暂时异常重试耗尽后均以 `gift.delivered` 路由到 `wallet.domain.dlx`，再由 durable 的 `live.gift.delivered.dead.queue` 接收；临时实时展示队列不能消费资金事实。礼物展示写入 durable `live.realtime.broadcast.exchange`（Fanout），客户端按原 `eventId` 去重。

`wallet.domain.exchange` 与 `wallet.domain.dlx` 都声明为 durable、非 auto-delete 的 Topic Exchange。`wallet-service` 只负责声明这两个领域交换机并发布已提交事实；`live.gift.delivered.queue` 及其死信绑定由 `live-service` 声明，避免生产者越权管理消费者队列。

| 级别 | 示例 | 丢弃规则 |
| --- | --- | --- |
| `CRITICAL` | 充值、扣款、收益、退款、风控处置 | 不能丢；积压、重试、死信和人工重放 |
| `IMPORTANT` | 礼物展示、开播通知 | 不主动丢；可限速、合并或发送摘要 |
| `BEST_EFFORT` | 点赞、热度、曝光 | 可用 Redis 聚合、TTL 或快照重算 |
| `EPHEMERAL` | 心跳、输入状态、在线刷新 | 可丢；直接走 WebSocket 或 Redis TTL |

## 7. Outbox、Inbox 与发布任务

资金事务将订单、余额、流水、收益和 `outbox_event` 一起提交。发布器扫描 `NEW`、已到 `next_retry_at` 的 `RETRY_WAIT`，以及租约过期的 `PUBLISHING`；领取短事务使用 `FOR UPDATE SKIP LOCKED` 按 `id` 取一批记录，写入随机 `lease_owner` 和 `lease_until` 后立即提交。RabbitMQ 发送发生在领取事务之外，不持有数据库行锁，也不进入账户 MySQL 命名锁边界。

每条消息以 `event_type` 作为 `wallet.domain.exchange` 的 routing key，body 使用 Outbox 已提交的 payload，并以原 `eventId` 创建 `CorrelationData`、AMQP correlation id 和 `x-outbox-event-id` header；`x-outbox-lease-owner` 供 mandatory return 找回当前领取。Publisher Confirm ACK 才把事件转为 `PUBLISHED`。Confirm NACK、发送异常或 mandatory return 只允许以 `(eventId, leaseOwner, status=PUBLISHING)` 更新当前租约，避免过期 worker 的迟到 callback 覆盖重新领取后的状态；Return 与 Confirm 竞态时，先成功转出 `PUBLISHING` 的路径生效，后到更新返回 0。

失败时沿用原 `eventId` 并将 `retry_count` 加一。第 1、2、3 次失败分别在约 1、2、4 秒后重试，后续按 `min(60s, 2^(retryCount-1)s)` 退避；达到 `wallet.outbox.max-retries` 后保留记录并标记 `DEAD`，不再自动领取，须经人工审计后重放。发布器不会因单条同步发送异常中断同批其他事件，也不能吞异常后标记成功。

`live-service` 收到事件后，按 `eventId` 写 `live_inbox_event`。已成功事件直接 ACK；首次事件在本地事务内写入 `PROCESSING`、构建并发送包含钱包礼物快照与结算快照的展示消息，随后更新为 `SUCCEEDED` 再 ACK。若展示发送结果不确定，事务回滚并重投同一 `eventId`，展示层负责去重；暂时性异常抛出以触发重试，不可恢复错误 reject 至死信。禁止捕获异常后只记录日志并确认资金消息。

## 8. 配置、发布与回滚

`wallet-service` 使用独立 `yuanlive_wallet` 数据库，数据库凭据由部署环境提供。Outbox 配置为 `wallet.outbox.publish-interval-ms`（默认 `1000`）、`wallet.outbox.batch-size`（默认 `50`）、`wallet.outbox.lease-seconds`（默认 `30`）和 `wallet.outbox.max-retries`（默认 `8`）；部署环境可分别通过 `WALLET_OUTBOX_PUBLISH_INTERVAL_MS`、`WALLET_OUTBOX_BATCH_SIZE`、`WALLET_OUTBOX_LEASE_SECONDS`、`WALLET_OUTBOX_MAX_RETRIES` 覆盖。Spring AMQP 必须开启 `publisher-confirm-type=correlated`、`publisher-returns=true` 和 mandatory。Nacos 或部署环境还需配置单次礼物数量上限、默认抽成和结算规则版本。`wallet.recharge.simulation-enabled` 默认关闭，仅开发或测试环境可通过 `WALLET_RECHARGE_SIMULATION_ENABLED=true` 显式开启；生产环境禁止设置为 `true`。

本地 Docker 首次启动由 `docker/docker-compose.yml` 中的 `MYSQL_DATABASE=yuanlive_wallet` 创建钱包库，并以只读挂载执行 `yuanlive-server/yuanlive-wallet-service/src/main/resources/db/wallet-schema.sql`。该 DDL 同时被钱包模块的 Testcontainers 集成测试使用，避免开发环境和测试环境出现两份表结构。初始化 SQL 以 UTF-8 保存，且首先执行 `SET NAMES utf8mb4`，使中文表、列注释按 UTF-8 写入。MySQL 的 `/docker-entrypoint-initdb.d` 只会在空数据目录执行；已有 `docker/mysql/data` 时，须先备份并由维护人员显式执行注释升级脚本，不能误以为重启 Compose 会自动迁移。

已有库的中文注释升级使用 `yuanlive-server/yuanlive-wallet-service/src/main/resources/db/V20260825_01__add_wallet_comments.sql`。执行时必须显式指定 `utf8mb4` 客户端字符集，不能使用容器内默认 `latin1` 的 `mysql` client 管道导入，否则 UTF-8 脚本中的中文注释会被按 `latin1` 解码并写成乱码：

```bash
docker exec -i -e LANG=C.UTF-8 yuanlive-mysql \
  mysql --default-character-set=utf8mb4 -uroot -pyuanlive yuanlive_wallet \
  < yuanlive-server/yuanlive-wallet-service/src/main/resources/db/V20260825_01__add_wallet_comments.sql
```

该升级脚本可重复执行，仅通过 `ALTER TABLE ... MODIFY COLUMN` 保留原字段类型、空值、默认值和 `ON UPDATE` 后更新字段注释，并通过 `ALTER TABLE ... COMMENT` 覆盖表注释；不删除数据、索引或表。注释错误时，以修订后的同类升级脚本再次覆盖元数据，禁止通过删库、删表或重建资金表回滚。后续结构演进必须引入版本化迁移，不得修改历史初始化脚本来替代迁移。

`live-service` 通过 Spring Boot Flyway 在启动时执行 `classpath:db/migration`。`V20260825_00__initialize_live_room.sql` 只以 `CREATE TABLE IF NOT EXISTS` 创建 `LiveRoom` MyBatis 映射所需的最小 `live_room` 基表，供全新空库启动；它不复制历史直播业务表或数据。`V20260825_01__add_live_room_accepting_gifts.sql` 保持只增加 `accepting_gifts TINYINT(1) NOT NULL DEFAULT 1`（默认允许收礼）和 `(room_status, accepting_gifts)` 房间预校验索引。`V20260825_02__create_live_inbox_event.sql` 创建 `live_inbox_event`，以 CosId `BIGINT` 主键和 `event_id UNIQUE` 实现消费幂等，DDL 不使用 `AUTO_INCREMENT`。部署前，运行账号必须拥有直播表的 `CREATE`、`ALTER` 权限；实例仅可在三条迁移成功执行、健康检查通过后接收流量。

既有非空直播库没有 `flyway_schema_history` 时，配置 `baseline-on-migrate=true` 和基线版本 `0`：Flyway 先登记版本历史，再依序登记/执行 `V20260825_00`（`live_room` 已存在时无操作）、`V20260825_01` 与 `V20260825_02`。全新空库不做基线，依序执行同样三条迁移并得到可用的最小 `live_room` 与 Inbox。已存在版本历史的数据库按历史表继续校验和迁移。回滚时先停止直播礼物消费者，保留 `live_inbox_event`、死信队列和消息，避免丢失可审计重放依据；不得用回滚脚本删除 Inbox、`accepting_gifts` 列或最小基表。

发布顺序：创建数据库与初始礼物目录；声明 Topic/DLX/队列；发布钱包只读与充值能力；发布送礼事务与 Outbox；发布直播消费者与展示；开放网关路由；禁用客户端礼物聊天入口。

回滚时先停止送礼入口，再停止钱包 Outbox 发布调度，保留已创建订单、流水与 Outbox。恢复发布器后，`NEW`、到期 `RETRY_WAIT` 和租约过期 `PUBLISHING` 按原 `eventId` 补发；不得删除资金记录、修改历史流水、清空 `DEAD` 或重新生成事件标识。`wallet.domain.exchange`、`wallet.domain.dlx` 及新增队列应继续保留，只有确认无绑定、无待重放消息且消费方已回滚后才能由运维显式删除。仅需撤销本地空库初始化时，可停止 Compose 后移走对应的开发数据目录再重新初始化；已承载资金数据的数据库不得通过删除数据目录回滚。

## 9. 可观测性与对账

记录 `traceId`、`userId`、`roomId`、`orderNo`、`eventId`。监控待发布 Outbox 数量及最老年龄、重试和死信数、队列积压、Inbox 失败/长期处理中记录、送礼成功率与订单到展示延迟。每日按订单号核对礼物订单、钱包流水、主播收益、Outbox 与 Inbox；对账任务只报告异常和处理线索，不直接改资金数据。
