# 阶段 1 前端适配 SPEC

## 1. 系统边界

钱包服务是资金事实唯一来源；客户端只负责发起请求、展示结果和维护临时交互状态；管理端只负责管理员只读查询。礼物展示是可靠消息产生的异步副作用，不改变订单状态。

```text
客户端礼物面板
  -> POST /wallet/gift-orders
  -> wallet-service 本地资金事务
  -> gift.delivered
  -> live-service
  -> live.realtime.broadcast.exchange
  -> WebSocket
  -> 客户端按 eventId 去重展示
```

## 2. 客户端设计

### 2.1 API 与类型

在 `yuanlive-tauri/src/api` 增加钱包 API 模块，在 `src/api/types.ts` 增加以下类型：

- `WalletAccountResult { userId: string; availableCoin: number; status: string }`
- `RechargeOrderResult { orderNo: string; status: string; availableCoin?: number }`
- `GiftCatalogItem { id: number; code: string; name: string; icon: string; unitCoinAmount: number; status: "ON_SHELF" }`
- `GiftOrderResult { orderNo: string; status: string; coinAmount: number; anchorIncomeAmount: number; availableCoin: number }`
- `LedgerQueryResult`、`IncomeQueryResult`、`GiftOrderQueryResult` 和 `CursorPage<T>`

请求封装必须保留后端 `Result` 的业务错误信息，不能把余额不足、处理中和礼物不可用统一显示为网络错误。

### 2.2 钱包 Store

扩展或新增 Pinia store，集中维护：

- `account`：当前余额和账户状态。
- `giftCatalog`：服务端礼物目录及加载时间。
- `pendingGiftRequests`：按 `requestId` 记录提交中的请求，防止重复点击。
- `recentEventIds`：有界集合，保存最近礼物展示事件用于去重。

`requestId` 使用浏览器 UUID。首次提交失败但业务明确允许重试时，必须复用原值；成功或明确不可重试后才清理。

### 2.3 直播间交互

`LivePlay.vue` 的礼物面板只使用 `GiftCatalogItem` 渲染，不再读取本地价格作为扣款依据。提交内容严格为：

```json
{
  "requestId": "UUID",
  "roomId": 10001,
  "giftId": 12,
  "count": 3
}
```

提交前显示服务端余额和单价，提交后以 `GiftOrderResult` 更新余额。余额不足时提供充值入口；处理中时禁止重新生成新的 `requestId`。

### 2.4 WebSocket 展示

Rust WebSocket 层将礼物展示消息转发为前端业务事件；消息至少包含：

`eventId`、`orderNo`、`roomId`、`senderId`、`anchorId`、`giftId`、`giftName`、`giftIcon`、`giftCount`、`coinAmount`。

前端收到消息后先判断当前房间，再按 `eventId` 去重，最后根据 `showGiftMessages` 和 `hideEffects` 决定文字提示与特效。去重只影响展示，不调用任何资金接口。

## 3. 管理端设计

### 3.1 路由与权限

新增财务模块路由，例如 `/finance/gift-orders`，由后端动态路由下发。建议权限点：

- `finance:giftOrder:list`
- `finance:giftOrder:detail`
- `finance:reconciliation:view`

页面只显示查询按钮和详情入口，不显示会修改资金或消息状态的操作按钮。

### 3.2 订单列表与详情

列表支持订单号、送礼用户、主播、订单状态和游标分页。详情按订单号并行请求礼物订单、对账报告；对账报告展示：

- 订单、扣款流水、主播收益是否存在。
- Outbox 是否存在及状态。
- Inbox 是否存在及状态。
- 后端返回的异常列表。

前端不得根据缺失记录自动刷新、补请求或推断资金结果为成功。

## 4. 错误与兼容策略

- HTTP 401/406 沿用现有 Token 刷新机制。
- 业务错误保留后端中文提示，并按错误场景提供下一步动作。
- 未识别的 WebSocket 消息只记录诊断信息，不阻断普通聊天。
- 旧版本客户端发送 `CHAT(type=gift)` 时由后端拒绝；新客户端不再生成该消息。
- 礼物展示字段缺失时丢弃展示消息并记录日志，不能修改订单或发起退款。

## 5. 测试与验证

客户端：API/store 单测、礼物面板组件测试、`requestId` 幂等测试、WebSocket `eventId` 去重测试。

管理端：API 参数测试、权限路由测试、订单详情异常渲染测试、游标分页测试。

联调：充值、重复充值、送礼成功、重复送礼、余额不足、房间不可收礼、RabbitMQ 延迟补发、重复展示和管理员越权查询。

## 6. 配置与发布

- 客户端 API 基地址必须指向含 `/wallet/**` 网关路由的环境。
- 模拟充值按钮只在开发/测试环境显示，并由后端 `wallet.recharge.simulation-enabled` 决定最终是否可用。
- 生产环境隐藏模拟充值入口，不能仅依赖前端开关保证安全。
- 发布顺序：后端只读接口 -> 客户端 API/store -> 客户端直播交互 -> 管理端页面/权限 -> 联调和灰度。
