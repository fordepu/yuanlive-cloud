# 阶段 1 前端适配 PRD

## 1. 产品目标

将阶段 1 后端钱包、充值、礼物订单、收益和可靠消息能力接入两个前端项目：

- 客户端 `yuanlive-tauri`：完成用户余额、模拟充值、HTTP 送礼和礼物实时展示闭环。
- 管理端 `yuanlive-admin`：完成财务管理员的订单检索、资金关联查询和只读对账。

前端不得自行计算礼物价格、主播收益或平台抽成；所有资金结果以钱包服务返回为准。

## 2. 用户与场景

| 用户 | 场景 | 期望结果 |
| --- | --- | --- |
| 普通用户 | 查看余额和金币流水 | 看到自己的实时余额及可追溯流水 |
| 普通用户 | 模拟充值 | 创建充值订单，支付成功后余额刷新且重复操作不重复入账 |
| 观众 | 直播间送礼 | 选择服务端礼物，提交订单后看到明确结果 |
| 观众/主播 | 接收礼物展示 | 每个礼物事件最多展示一次，展示失败不影响账务 |
| 主播 | 查看收益 | 查看自己的收益记录和订单关联信息 |
| 财务管理员 | 查询异常订单 | 按订单号查看订单、流水、收益、Outbox、Inbox 和异常原因 |

## 3. 范围

### 包含

- 客户端钱包 API、类型、状态管理和钱包页面。
- 客户端直播间礼物目录、数量选择、余额展示和送礼反馈。
- 客户端 `requestId` 生成、请求中防重复提交和网络重试复用。
- 客户端礼物展示消息解析及 `eventId` 去重。
- 管理端礼物订单查询、订单详情和只读对账页面。
- 管理端财务权限、动态菜单和异常状态展示。
- 前后端联调、前端单元测试、类型检查、构建和关键流程 E2E。

### 不包含

- 真实支付渠道、提现、出金、冲正和退款产品。
- 前端修改余额、收益、流水或订单状态。
- 人工死信重放、后台补账和资金修复操作。
- 客户端通过 `CHAT(type=gift)` 完成送礼。

## 4. 后端配套接口

现有接口继续作为前端唯一资金入口：

```text
GET  /wallet/accounts/me
POST /wallet/recharge-orders
POST /wallet/recharge-orders/{orderNo}/simulate-paid
POST /wallet/gift-orders
GET  /wallet/query/gift-orders/{orderNo}
GET  /wallet/query/ledgers?beforeId=<id>&limit=<limit>
GET  /wallet/query/incomes?beforeId=<id>&limit=<limit>
GET  /wallet/query/reconciliation/gift-orders/{orderNo}
```

为满足客户端礼物目录和管理端列表需求，后端需新增只读接口：

```text
GET /wallet/query/gifts
GET /wallet/query/admin/gift-orders?orderNo=&senderId=&anchorId=&status=&beforeId=&limit=
```

新增接口约束：

- 礼物目录只返回状态为 `ON_SHELF` 的上架礼物及其服务端价格、图标和展示信息。
- 管理端订单列表仅允许管理员角色访问，最多返回 100 条，使用 `id` 游标分页。
- 管理端查询只读，不提供补账、改余额、重发事件或死信重放操作。

## 5. 验收标准

- 同一 `requestId` 的重复提交不会产生第二笔扣款、收益或订单。
- 客户端不向送礼接口提交价格、主播、图标、抽成或收益字段。
- 余额不足、礼物下架、房间未开播和主播不可收礼时，界面展示明确错误且不伪造成功。
- 充值成功后余额可刷新；重复模拟支付只显示原订单结果。
- 礼物展示消息按 `eventId` 去重，重连或重复投递不会重复展示。
- `CHAT(type=gift)` 被前端禁止发送；普通文本聊天和点赞保持可用。
- 普通用户只能查看自己的订单、流水；主播只能查看自己的收益。
- 管理员可以按订单号查看完整只读对账报告和异常关联键。
- 两个前端项目完成类型检查、单元测试和生产构建；关键联调场景通过。

## 6. 发布原则

先发布后端礼物目录和管理员订单列表只读接口，再发布客户端和管理端。后端接口未就绪时，前端不得用写死价格或本地模拟订单替代正式链路。
