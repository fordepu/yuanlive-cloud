# 阶段 1 送礼资金闭环 PRD

## 1. 产品目标

让用户能够安全地充值和送礼，让主播能够查询可核对的收益，让平台能够按订单追踪每一笔金币变化。首版以“送礼资金闭环 MVP”为边界，不引入真实支付、提现、出金、公会结算和活动定价。

## 2. 用户与场景

| 用户 | 场景 | 期望结果 |
| --- | --- | --- |
| 普通用户 | 查询金币余额 | 获得当前可消费金币和流水明细 |
| 普通用户 | 模拟充值 | 订单支付成功后余额只增加一次 |
| 观众 | 在开播房间送礼 | 扣款成功后看到礼物展示；网络重试不重复扣款 |
| 主播 | 查看收益 | 能按礼物订单追溯收益和平台抽成 |
| 财务管理员 | 查询异常订单 | 能定位订单、流水、收益和事件投递状态 |

## 3. 首版范围

### 包含

- 用户钱包自动开户、余额和流水查询。
- 受控模拟充值、充值订单与幂等回调。
- 固定礼物目录、礼物价格与上架状态。
- 送礼扣款、主播收益、平台抽成和订单结算快照。
- 房间实时礼物展示。
- `requestId` 请求幂等、可靠消息投递、重复消费防护、死信和对账入口。
- 钱包与财务管理员权限、`/wallet/**` 网关路由。

### 不包含

- 真实支付渠道、法币余额、提现、出金与法币清结算。
- 用户之间转账、金币转让、主播收益兑换。
- 公会分成、主播差异化抽成、活动价格、连击特效和榜单产品页。
- “没有收到 WebSocket 特效就自动退款”的展示确认机制。

## 4. 产品规则

| 主题 | 规则 |
| --- | --- |
| 金币 | 使用整数金币；固定兑换率 `1 元 = 10 金币` |
| 礼物价格 | 由服务端礼物目录决定；客户端不能传价格、图标或主播收益 |
| 送礼入口 | 使用 HTTP 订单接口；WebSocket `CHAT(type=gift)` 不再能够完成送礼 |
| 重试 | 客户端对同一次点击复用同一个 `requestId` |
| 历史结算 | 订单固化礼物价格、兑换率、抽成比例和规则版本；历史查询不按现行配置重算 |
| 房间关闭 | 扣款提交后房间关闭不自动退款；保留账务事实，停止或降级实时展示 |
| 退款/冲正 | 只允许新增反向流水和冲正订单；不修改历史流水 |

## 5. 核心体验与接口

### 5.1 模拟充值

用户创建充值订单后，在受控开发或测试环境完成模拟支付。系统校验订单归属和状态后入账；重复回调返回已完成结果但不增加第二次余额。

### 5.2 送礼

客户端提交：

```json
{
  "requestId": "e43f4ad5-4489-4b7e-b7f7-e2e6283f25ee",
  "roomId": "10001",
  "giftId": 12,
  "count": 3
}
```

系统返回订单号、订单状态、扣款金币和剩余余额。余额不足、礼物不可用、房间未开播、重复请求和处理中请求都必须返回可识别的业务结果。

## 6. 验收标准

- 同一个 `requestId` 的送礼重试不会重复扣款、加收益或发送礼物展示。
- 余额、订单、流水、主播收益可以按订单号相互追溯。
- 余额不足、礼物下架、房间未开播和主播不可收礼均不产生扣款。
- 充值和送礼的重复回调、重复消息、服务重启后补发均不产生重复业务结果。
- 已成功订单在 RabbitMQ 暂时不可用时可在恢复后补发礼物事件。
- 礼物事实与普通聊天、点赞和心跳使用隔离的消息策略；资金事实不允许因高峰被丢弃。
- 观众和主播能够收到一次可去重的礼物展示消息；展示失败不改变已完成账务。
- 普通用户只能查询自己的礼物订单、金币流水；主播可查询自己的收益，管理员可按订单查看只读对账报告。
- 对账发现订单、流水、收益、Outbox 或 Inbox 缺失/状态异常时只报告异常和关联键，不自动修改资金数据。

## 7. 非功能要求

- 金额使用 `long`，禁止 `double`。
- 资金链路必须有 `traceId`、`userId`、`roomId`、`orderNo` 和 `eventId` 日志字段。
- 关键路径使用 Testcontainers 的 MySQL 与 RabbitMQ 集成测试，不依赖开发机已有中间件或数据。
- 详细实现边界见 [SPEC](../specs/2026-08-25-阶段1送礼资金闭环-spec.md)，实施顺序见 [Plan](../plans/2026-08-25-阶段1送礼资金闭环-plan.md)。
