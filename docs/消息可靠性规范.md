# 消息可靠性规范

## 1. 适用范围

本规范适用于会改变业务状态或需要审计的 RabbitMQ 消息。钱包、礼物、收益、退款、风控处置等资金与治理事件必须遵守本规范。

现有直播聊天、在线状态和普通通知消息可逐步迁移；在未迁移前不因本规范改变既有消息格式。

## 2. 事件信封

业务事件通过 JSON 信封传递，禁止只发送无法追溯来源的业务对象。

```json
{
  "eventId": "01J...",
  "eventType": "gift.delivered",
  "payloadVersion": 1,
  "occurredAt": "2026-08-24T12:00:00Z",
  "traceId": "...",
  "businessId": "gift-order-no",
  "payload": {}
}
```

字段约束：

| 字段 | 说明 |
| --- | --- |
| `eventId` | 全局唯一事件标识，也是消费端幂等键。一次业务事件重试时必须保持不变。 |
| `eventType` | 稳定的领域事件名称，例如 `gift.delivered`、`wallet.balance.changed`。 |
| `payloadVersion` | 消息结构版本。字段新增应保持兼容；不兼容变更必须递增版本。 |
| `occurredAt` | 事件完成时间，使用 UTC ISO-8601。 |
| `traceId` | 从 HTTP、Feign 或 WebSocket 链路继承；异步消费日志必须继续使用该值。 |
| `businessId` | 订单号、直播间 ID 或审核单号等可供人工定位的业务标识。 |
| `payload` | 具体业务数据；金额类字段使用整数最小单位，不使用 `double`。 |

## 3. 生产端规则

1. 在本地数据库事务内写业务数据、审计流水与 Outbox 记录。
2. Outbox 发布器读取未投递记录，向 RabbitMQ 发布事件，并记录发布时间和投递结果。
3. 发布失败只能重试同一 `eventId`，不得生成新事件后掩盖旧事件失败。
4. 资金事件必须启用发布确认和不可路由回调；无法路由的事件保留待人工处理。
5. 消息体不得包含密码、Token、支付验签原文或完整敏感内容。

## 4. 消费端规则

1. 消费前以 `eventId` 检查幂等记录；已成功处理则直接确认消息。
2. 业务处理和“消费成功记录”必须在同一数据库事务内提交。
3. 临时错误进入有限次数重试；重试次数耗尽后路由到死信队列。
4. 参数校验失败、版本不支持和不可恢复业务错误直接进入死信队列，并记录原因。
5. 死信重放必须复用原始 `eventId`，且记录重放人、时间、原因和结果。

关键事件监听器应显式指定 `containerFactory = "reliableRabbitListenerContainerFactory"`。该工厂提供 3 次有限重试（1 秒、2 秒、4 秒）并在耗尽后拒绝重新入队；对应队列必须配置死信交换机，避免消息被无声丢弃。

## 5. 幂等记录最小字段

```text
event_id       唯一索引
event_type
business_id
status         PROCESSING / SUCCEEDED / FAILED
processed_at
failure_reason
```

资金相关消费者还应通过业务唯一键约束二次保护，例如礼物订单号、钱包流水号和收益记录号。

## 6. 迁移顺序

1. 钱包和礼物事件从第一版开始使用 Outbox、事件信封、幂等记录和死信队列。
2. AI 风控审核事件随后迁移，以便审核动作可重放和审计。
3. 普通直播通知消息在不影响实时性的前提下逐步补充 `eventId` 与 `traceId`。
